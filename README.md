# 可穿戴设备端云协同与多模型选型评估报告

## 📖 一、 项目背景
针对智能可穿戴设备（如耳机）算力受限、电池容量小、网络环境复杂的物理痛点，本项目旨在通过客观的基准测试，验证**“端侧分流 + 云端推理”**架构的可行性与必要性，为智能硬件的 AI 大模型部署提供真实的数据支撑。

## 🏗️ 二、 评估方法
受限于缺乏真实耳机硬件，本次评估采用**物理约束仿真法（Hardware-constrained Software Simulation）**，严格模拟了端侧 MCU 的物理极限与云端 API 的真实网络环境：

1. **端侧本地处理（模拟耳机 MCU）**：极低算力，仅支持轻量级规则匹配；极速响应（设定 5ms 延迟）；0 Token 消耗。
2. **云端大模型推理（真实 API 调用）**：通过跨海 Codespaces 环境，真实调用 DeepSeek、智谱 GLM、阿里通义千问三款主流大模型。

## 📊 三、 实测数据
在相同的复杂推理指令（如“OpenComm2怎么开机？”）下，实测数据如下：

| 架构层次 | 处理位置 | 平均延迟 | 平均 Token 消耗 | 实测结论与架构建议 |
| :--- | :--- | :--- | :--- | :--- |
| **端侧本地模拟** | 耳机 MCU 芯片 | **5.08 ms** | **0** | 高频控制指令（如：下一首、暂停）必须在端侧拦截，保障零延迟和零成本。 |
| **云端 (DeepSeek)** | 海外 API 节点 | **2.22 s** | 323.0 | 逻辑推理最稳定，延迟适中，适合处理复杂知识问答。 |
| **云端 (智谱 GLM)** | 海外 API 节点 | **13.09 s** | 231.7 | 受跨国网络波动影响极大，延迟飙升，暴露了云端 API 在弱网下的致命脆弱性。 |
| **云端 (通义千问)** | 海外 API 节点 | **3.13 s** | 391.0 | 综合表现稳定，但 Token 消耗成本偏高。 |

*(注：以上数据基于 Codespaces 真实网络环境多次采样平均值)*

## 💡 四、 核心结论与架构决策
基于上述客观实测数据，得出以下可穿戴设备 Agent 的架构选型建议：

1. **端侧分流是物理必然**：如果把“下一首”这种高频指令传至云端，即使是最快的模型也要 **2秒以上** 的延迟，而放在端侧只需 **5毫秒**。这不仅影响用户体验，还会极大地消耗耳机电池。因此，必须在端侧构建轻量级的意图路由。
2. **云端模型选型需考虑网络拓扑**：同为轻量级模型，智谱 GLM 在跨海网络下延迟高达 13 秒，而通义和 DeepSeek 维持在 2-3 秒。这说明在真实的硬件产品中，**不能只看模型的理论能力，网络拓扑、地理节点和真实端到端延迟才是架构选型的决定性因素**。
3. **弱网降级策略**：实测暴露了云端 API 在弱网下的脆弱性，这直接推动了在产品架构中必须加入“本地缓存”或“离线兜底”策略。
